# Operator console

This directory is the operator console the Hub serves at `/console/`. It began as the [assistant-ui](https://github.com/assistant-ui/assistant-ui) starter project and is no longer that starter; what remains of it is described below.

The chat surface came from that starter, generated by these commands from the repository root on 2026-11-13:

```bash
ASSISTANT_UI_ALLOW_AGENT=1 npx --yes assistant-ui@latest create web -t default --use-pnpm
ASSISTANT_UI_ALLOW_AGENT=1 npx --yes assistant-ui@latest add thread thread-list markdown-text reasoning tool-fallback attachment tooltip-icon-button threadlist-sidebar --yes --use-pnpm --cwd web
```

`create` installed `@assistant-ui/utils`, `tooltip`, `sidebar`, `separator`, `breadcrumb`, `@assistant-ui/thread`, and `@assistant-ui/threadlist-sidebar`. The `add` command found those files already present and did not overwrite them.

`pnpm build` is the Vite embed the Hub serves at `/console/`. It opens straight to the operator workbench (`src/console/Workbench.tsx`); the assistant sits in the workbench rail and sends turns to the Hub at `POST /v1/assistant/turns`. The starter chat page, thread-list sidebar, element catalog and Codex bridge status UI are not part of the console. The Codex ACP bridge server still lives in `src/server` for local use. `pnpm dev:template` is the template's Next dev server and renders the same workbench.

The rest of the registry was added the same way, one item at a time, without overwriting files the CLI had already written:

```bash
ASSISTANT_UI_ALLOW_AGENT=1 npx --yes assistant-ui@latest add <item> --yes --use-pnpm --cwd web
```

`<item>` is every `elements-*` entry and the runtime items `voice`, `voice-conversation`, `task-card`, `agent-status`, `mcp-config`, `assistant-modal`, `assistant-sidebar`, `shiki-highlighter`, `model-selector`, `logos`, `heat-graph`, `directive-text`, and `generative-ui`.

## What the console writes to the Hub

`Workbench.tsx` mounts the operator engine in `src/console/operator/engine.js`. The engine reads the Hub through `live-hub.js` and does not use `src/console/data/hub.ts`. That file's plan approve and reject calls are reachable only through `data/useConsoleData.ts`, which nothing mounted imports; the React components that import `hub.ts` take types from it.

The delivery journey's writes live in `src/console/operator/delivery-actions.js` (request shapes and state) and `delivery-journey.js` (panels). Each one shows a confirmation with the exact request, disables its controls while the request is in flight, reports only what the Hub answered, and then reads the Hub indexes again.

| Action | Where | Request |
| --- | --- | --- |
| Propose a plan | Releases / Environments | `POST /v1/plans` with the next desired state; title and reason in `X-Change-Title` and `X-Change-Description` |
| Approve a plan | Releases / Plans, Change requests / Approvals | `POST /v1/plans/{planID}/approvals` `{rationale}` |
| Reject a plan | same | `POST /v1/change-requests/{changeRequestID}/reject` `{rationale}` when the plan has a change request, `POST /v1/plans/{planID}/cancel` `{reason}` otherwise |
| Evaluate a promotion | Releases / Promotion | `POST /v1/promotions/evaluations` `{release, fromChannel, toChannel, policy, evidence}` |
| Approve or reject a change request | Change requests | `POST /v1/change-requests/{changeRequestID}/approve` or `/reject` `{rationale}` |

Limits that are the Hub API's, not omissions in the table:

- A proposal edits a desired state the Hub already accepted (the newest plan of that environment) and moves one installation to a release the catalog lists. The first desired state of an environment is proposed with `conduit plan propose`.
- `POST /v1/plans` refuses an invalid document with only a count. The console then asks `POST /v1/validate`, which records nothing, for the rule that failed.
- A promotion is evaluated only across a stage the Hub already holds a policy for: one declared in a loaded desired state, or the policy of a recorded evaluation. The console does not author a promotion policy.
- The author of a change is shown why they cannot approve it and is offered no live button. The Hub enforces the rule either way.
- The Space selector in the top bar sends `spaceId` to `GET /v1/environments`, the only index route that reads it, and narrows installations, plans and change requests to the environments that came back. Products, promotions, channels, packaging, bundles and audit are not Space-scoped.
- Organization settings edits approval policies and resource grants after a separate review and confirmation. The Hub checks current authority and the submitted revision; conflicts require reloading rather than automatic overwrite. Teams remain read-only. Creating a Space, publishing a Product Release, and the suppressions, labels, export pipelines, commands, modules and artifact scans surfaces are CLI-only.

`src/console/operator/planning-flow.js` keeps the planning session id in the URL as `#s01-intake/<sessionId>` and reads the session and its events again on load. Stop aborts the stream in the browser. The Hub has no route that cancels a planning run or lists planning sessions, so Stop does not cancel the run on the Hub and there is no session list; the page says both. It lists the caller's app generations from `GET /v1/app-generations`.

`scripts/simulate-console.sh release-write-journey.spec.ts` runs the propose, approve, blocked-promotion and Space checks in `src/test/live/` against a real Hub.


## Running it

Use the Node and pnpm versions pinned in the repository's `mise.toml`.

| Command | What it does |
| --- | --- |
| `pnpm install --frozen-lockfile` | Installs the locked dependencies. |
| `pnpm dev` | Runs `src/server/dev.mjs`, which starts the Vite development server (`vp dev`). |
| `pnpm build` | Checks the toolchain and the generated live-event validator, then builds the embed. From the repository root, `./scripts/build-console.sh` runs this and writes `internal/consoleui/dist`, which the Hub serves at `/console/`. |
| `pnpm check`, `pnpm typecheck`, `pnpm test:unit`, `pnpm test:e2e` | The checks `pnpm test` runs in that order. `./scripts/test-console.sh` is what the Trunk gate runs. |

The served console holds no model key. The Codex ACP bridge in
`src/server/agent.ts` is the one place under `web/` that reads one
(`CODEX_API_KEY`, then `OPENAI_API_KEY`), for its own local use. A model provider is configured on
the Hub (`CONDUIT_MODEL_CMD` or `CONDUIT_MODEL_BASE_URL`; see
`docs/operations/local-model-cli.md` and `docs/operations/model-http.md`), and
the assistant rail reaches it only through the Hub.
