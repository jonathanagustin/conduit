=== AMBIENT MESH (recorded failure, by output) =================================
With AMBIENT_ENABLED=true the node agent exits:
  info cni-agent  creating host addressSet manager in the node netns
  Error: failed to create ambient nodeagent service: error initializing mesh
  dataplane: error initializing host addressSet manager: failed to Statfs
  "/host/proc/1/ns/net": no such file or directory
Every pod sandbox then failed:
  plugin type="istio-cni" ... failed to contact node Istio CNI agent ...
  dial unix /var/run/istio-cni/pluginevent.sock: connect: connection refused
ztunnel stays 0/1 for the whole session:
  warn inpod::workloadmanager failed to connect to the Istio CNI node agent
  over "/var/run/ztunnel/ztunnel.sock" ... Connection refused
Setting AMBIENT_ENABLED=false (what scripts/uds-up.sh does) lets sandboxes
start. Consequence, not predicted by the repo docs: UDS Core 1.17.1 puts the
keycloak namespace in ambient mode (istio.io/dataplane-mode=ambient, a
keycloak-waypoint, istio.io/use-waypoint on Service keycloak-http). Sidecar
clients send HBONE to <keycloak-pod>:15008, where nothing listens:
  sidecar log: "delayed_connect_error:_Connection_refused" ... "10.42.0.25:15008"
  connect_originate ... GET /realms/uds/... 503 URX,UF
  nc from an unmeshed pod: 10.42.0.25:15008 closed, :8080 open
So with ambient dead, Hub (sidecar) -> Keycloak and gateway -> Keycloak
(sso.uds.dev) both return 503. The Hub then exits at startup with
  ERROR configure operator OIDC identity error="discover OIDC issuer: 503
  Service Unavailable: upstream connect error ..."
EXPERIMENT (reversible, mine): removed label istio.io/dataplane-mode from ns
keycloak, removed istio.io/use-waypoint and istio.io/ingress-use-waypoint from
svc keycloak-http, deleted keycloak-0 (new pod has no ambient annotation).
After that: Hub-labelled pod -> keycloak-http:8080 200, -> https://sso.uds.dev
200, host -> gateway sso.uds.dev 200. To revert: re-add
  kubectl label ns keycloak istio.io/dataplane-mode=ambient
  kubectl -n keycloak label svc keycloak-http istio.io/use-waypoint=keycloak-waypoint istio.io/ingress-use-waypoint=true
(and delete keycloak-0). Not reverted: the cluster was left in this state.

=== Q7. #619 users, bearer, login ==================================================
scripts/uds-keycloak-users.sh, UDS_KEYCLOAK_URL=http://127.0.0.1:18080 (a
port-forward to keycloak-0; the https://keycloak.uds.dev default was 503 while
ambient was down). FINDING C: the script FAILED as shipped:
  curl: (22) The requested URL returned error: 400
because the uds realm enforces passwordPolicy length(15), specialChars(2),
digits(1), lowerCase, upperCase, passwordHistory(5), forceExpiredPasswordChange(60)
and the generated `openssl rand -base64 24` password has no guaranteed special
characters ("invalidPasswordMinSpecialCharsMessage: must contain at least 2
special characters"). Fixed in this branch; script test passes; both users
conduit-author and conduit-reviewer then created in group conduit-operators.
Tokens (grant_type=password, client admin-cli, Host: sso.uds.dev) carry
  iss=https://sso.uds.dev/realms/uds  azp=admin-cli  groups=["/conduit-operators"]
  aud=https://sso.uds.dev/admin/realms/uds
Hub (OPERATOR_OIDC_ISSUER=https://sso.uds.dev/realms/uds, client conduit-hub):
  GET /v1/session, no token                     401 {"error":"unauthorized"}
  GET /v1/session, Bearer <author token>        401
  GET /v1/session, Bearer <reviewer token>      401
Both bearer tokens were REJECTED. Likely cause (INFERRED, not proven by a log
line, the Hub logs only status=401): the verifier checks aud == conduit-hub
(oidcverifier.go) and these tokens carry the admin API audience. A token for
the conduit-hub client was not obtainable by password grant (client has
directAccessGrants false). So "a Keycloak user token is accepted" is NOT established.
GET /v1/auth/login: 302 to
  https://sso.uds.dev/realms/uds/protocol/openid-connect/auth?client_id=conduit-hub
  &code_challenge=<r>&code_challenge_method=S256&nonce=<r>
  &redirect_uri=https%3A%2F%2Fconduit.uds.dev%2Fv1%2Fauth%2Fcallback
  &response_type=code&scope=openid+profile+email&state=<r>
  Set-Cookie: __Host-conduit-login=<r>; Path=/; Max-Age=600; HttpOnly; Secure; SameSite=Lax
Following it with curl through the gateway to Keycloak and posting the author's
credentials: Keycloak accepted the password and redirected to
  /realms/uds/login-actions/required-action?execution=CONFIGURE_TOTP&client_id=conduit-hub
i.e. a script-created user must enrol TOTP before any code is issued. The Hub
callback was therefore never reached; sign-in completion is NOT established.
