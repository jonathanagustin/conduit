| PH-1 ([#20](https://github.com/jonathanagustin/conduit/issues/20)) | Requested during the bounded-context migration: "we want an automerge queue eventually". | A merge queue can keep `main` green without a person dispatching each verification run. | **QUEUED.** It cannot be built without overturning A4, which is CONFIRMED: repository-authored workflows run only after a person dispatches them. A merge queue is a workflow that runs on `merge_group` with no human in the loop, so this is not an implementation detail to work around -- it is the assumption itself. ADR 0001 gives the cost rationale behind A4 ("publication must remain manual because hosted Actions time is controlled"), and the Trunk gate inherits it. Overturning a CONFIRMED assumption for convenience is the repository owner's call, not an agent's, so this stays queued with the conflict stated rather than being quietly implemented or quietly forgotten. What would unblock it: a decision that automatic Actions consumption is acceptable for `merge_group` events specifically, recorded as a change to A4 with its cost. |
| PH-2 (no issue: REJECT) | Considered while recovering the Apollo GraphQL surface. | A gate should fail when the pinned upstream `apollo-openapi` snapshot drifts from its source, so a stale pin cannot pass unnoticed. | **REJECT.** The pinned snapshot is byte-identical to upstream HEAD and that repository has been dormant since 2024-09-19. A gate over it would pass unconditionally for as long as that holds, and a check that cannot currently fail reads as coverage while providing none -- the same defect this repository's planted-violation tests exist to prevent. It was never implemented, and this row records why so the idea does not resurface as an oversight. Revisit if upstream resumes: the useful trigger is upstream moving, not a scheduled poll. |
| PH-3 ([#21](https://github.com/jonathanagustin/conduit/issues/21)) | Deferred while wiring the Gitless GitOps scheduler. | A scheduled Gitless source change can be proposed into Conduit's governed Plan pipeline. | **QUEUED — needs a decision, not code.** `GITLESS_CONVERGENCE=conduit` is unwired because proposing desired state requires a principal holding `change:propose` on the environment (`internal/governance/domain/authorization.go`), and the scheduler is a background loop with no request and no identity. Three options, all governance decisions: (a) a dedicated service principal granted `environment:editor` on each bound environment, which means whoever can publish to the registry effectively holds propose authority; (b) a system principal that bypasses authorization, which invents authority and is refused everywhere else in this codebase; (c) an operator nominates a principal per binding in configuration, which is the most consistent with the existing model and the current recommendation. Until one is chosen the path refuses at startup rather than starting something that cannot work, and no adapter is built for it -- an unwired adapter is the island problem this context was written to avoid. |
| PH-4 ([#22](https://github.com/jonathanagustin/conduit/issues/22)) | Stated as a bound while building the resolution log. | The Gitless resolution log can be durable across Hub replicas. | **QUEUED — trigger is multi-replica, not now.** `adapters/resolutionlog` is one file on one filesystem, fsynced before the deployment it records. That is correct for a single-replica Hub and wrong for several: two Hubs would each hold a partial history, and the port's contract -- record before deploying, so nothing is unattributable -- would hold per replica rather than per fleet. The replacement is a PostgreSQL adapter behind the same `ports.ResolutionLog`, which needs a migration and the existing Postgres test harness. Not built speculatively: it should land with the first multi-replica deployment, and the bound is stated in the package comment and the operator guide so that deployment cannot happen unaware. |
| PH-5 ([#15](https://github.com/jonathanagustin/conduit/issues/15)) | Found by re-crawling the public documentation on 2026-08-15 after the corpus had gone six weeks without one. | Conduit implements Apollo's published Environment connection settings. | **QUEUED — a behaviour decision, not a missing constant.** Apollo now publishes five connection settings; `internal/environments/domain/federation.go` implements the four that were the whole published set on 2026-08-02. The fifth is `Intermittent agents`: Agents connect directly and Plans ARE issued, health displays as of the last connection, Bundle import stays disallowed, and it supports Release Channel promotion. What separates it from `AGENTS_CONNECTED` is that gaps in reported state are expected and are NOT an outage. Adding a bare constant would be worse than leaving it out, because `IssuesPlans`, `AcceptsAgentConnections`, `AcceptsRelayedState` and `TracksHealth` are all equality against `ConnectionAgentsConnected`, so the new state would accept no Agents, issue no Plans and block promotion -- the opposite of what Apollo publishes. The harder half is staleness: Conduit reads a stale report as `HealthUnknown`, which is right for a continuously-connected Environment and wrong for an intermittent one where the same silence is expected, and that feeds promotion evidence. Deciding how an intermittent Environment vouches for a Release is the actual question. |
| PH-6 ([#13](https://github.com/jonathanagustin/conduit/issues/13)) | Found while regrounding the corpus: the CEL examples page publishes `require_operation(rid, "entity:approve-config-update", ...)`. | An upstream-authored CEL policy using a published operation name is satisfiable here. | **CONFIRMED — and the proposed fix was wrong.** The hypothesis holds: an Apollo-authored policy naming `entity:approve-config-update` matches nothing here, so the change is unapprovable and nothing says why. The *reasoning* recorded here was wrong, and it was wrong in the direction that would have caused damage. It said the operation "matches no grant and no role" and concluded the vocabulary should be closed and validated like the Change Type taxonomy. It does match a grant: `RequirementSatisfied` compares `requirement.Operation` against `ResourceGrant.Operations`, which `PutGrant` deliberately does not constrain, so an operator-defined approval token is a working feature — `TestCELRoleAndOperationRequirementsUseResourceGrants` has exercised `environment:approve-change` end to end since before this row was written. Validating `require_operation` against the operation constants compiles, passes review, and silently deletes that feature; it was implemented, caught by that test, and reverted. The operation constants are what Platform *performs*; grant operations are what a policy may *demand*, and the two namespaces only share a field. Re-scoped: the real defect is that a requirement nothing can satisfy stays pending forever instead of being reported, which is a question about grants at evaluation time, not about a vocabulary at authoring time. |
| PH-7 ([#16](https://github.com/jonathanagustin/conduit/issues/16)) | Found by mining `core/whats-new`, which had been in the corpus since 2026-08-01 and never read. | Conduit implements Apollo's scan-before-install constraint. | **QUEUED.** It does not. The 2026-06-11 entry announces "a constraint that enforces that a Release has passed a security scan before it can be installed in Environments... controlled by a Space setting to enforce that a scan must occur before an upgrade can proceed." Conduit scans exact artifact digests, scores risk, and gates the CVE-recall upgrade exception on scan freshness, but nothing blocks an install or upgrade because a scan has *not happened*. `RequireMalwarePass` is the closest thing and is not it: it gates what enters a Bundle at export, not whether an Entity may move version in an Environment. Two things need deciding before code: the constraint is a Space setting and Conduit has no Space (PH-5's neighbour), and "has been scanned" needs a freshness rule or an Entity pinned to an old Release would be permanently blocked by a scan record that has aged out. |
