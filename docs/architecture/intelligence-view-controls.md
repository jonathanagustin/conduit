# Native Intelligence evidence and proposal controls

The four existing Intelligence views remain the only homes for Logic, Evals,
Courses and Automations. The assistant rail is not duplicated. Logic and Courses
share a scoped memory-proposal form rather than hidden demo target coordinates.
Targets come from the visible desired fleet index; observed-only rows are not
treated as desired targets. The existing deterministic course-scoring route
supplies outcomes and trade-offs. Missing/blocked results cannot be staged.

The form requires explicit confirmation of the displayed target and value;
edits clear confirmation. Submission uses the existing course-select endpoint.
The Hub resolves the actual caller through its operator carrier, checks proposal
permission on the target installation and verifies the installation/Product
against current desired fleet state. Failed memory gates cannot reach the
proposal opener. Native target identity hashes the full resolved caller plus
Environment, installation, Product and value, preventing cross-target reuse.
The response reports the validated coordinates and is checked by the client.
The existing mandatory-human-review method is preserved. No automatic approval,
execution, lease or publication endpoint is called, and the native intelligence
target has no workload actuator. A repeated scoped proposal retains its native
request identity. Uncertain responses do not trigger automatic retries; the UI
requires inspection of change requests.

The displayed configured gate and adapter mode are configuration, not evidence
that a model ran. This studio does not call the legacy packaging model-proposal
route, whose deployment target binding is not supplied here. Scoped manual
memory proposals use the governed path above. Rule persistence/version editing,
recommendation ranking, measured simulations and hidden reasoning traces are not
invented. Only supplied gate reasons and native request metadata are shown.

Evals display supplied cases separately from observed adapter columns. Summary
counts mean expectations matched: a required failure that was expected is a
matching test, not a deployment pass. Run is explicit and may use the configured
adapter for its supported case. Feedback-case capture requires confirmation and
states that the current service does not persist cases across Hub restart.
These results do not establish deployment or independent live-provider proof.

Automations show supplied observed runs and label the service's non-executing
example rules. The current API provides no pause or rule-persistence endpoint;
those controls stay unavailable rather than changing local state as though a
rule were paused. Empty observed data means none was supplied, not proof of no
runs. All text is escaped, displayed cases/runs are bounded, superseded mounts
cannot apply late results, and associated request navigation uses the existing
review view after refreshing its native index.

These are Conduit extensions, not private protocol compatibility. Remaining rule
persistence/trials, resolved model deployment proposals, recommendation metadata
and live automation controls remain tracked in #555.
