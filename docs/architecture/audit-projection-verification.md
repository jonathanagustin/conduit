# Audit projection verification and provenance

The existing administrator-only `GET /v1/authorization-audit?view=chain` now returns the exact base64 payload bytes, resource identifier and origin used by each returned digest. The existing endpoint permission is retained. The domain builds this projection by folding recorded events from genesis in read order: chain sequence on PostgreSQL, event time and then ID on the memory and file stores. It is not the persisted PostgreSQL ledger's digests or independently retained checkpoint. No persisted chain is rewritten.

Since issue #841 the read is paginated (`limit` default 100, maximum 200, `cursor`, `since`, `until`; see `docs/ui/contracts/pagination.md`). Each `view=chain` page continues from the projection checkpoint carried in its cursor, so a client must concatenate every page, following `nextCursor`, before verifying from genesis; a single page after the first cannot pass on its own. A cursor is not authenticated: a forged checkpoint only produces a projection that fails that verification.

The existing Audit view adds a separate returned-payload verification button alongside its link check. Browser SHA-256 uses the native version prefix, big-endian uint64 sequence, and length-framed predecessor, event ID, resource, origin and exact payload bytes. It checks displayed identity coordinates against decoded payload and verifies every digest and link from genesis. Missing payloads, unknown origin, malformed base64/UTF-8, missing prefixes, inexact JavaScript sequences and mismatches cannot pass. Empty evidence is unavailable, not verified. Work is bounded to 10,000 entries, 2.8 MB base64 per payload and 20 MB encoded payloads in total. A data refresh clears the previous result; asynchronous verification cannot overwrite a newer projection.

A successful check states only that returned payloads and links are internally consistent. It does not attest event truth, server honesty, at-rest integrity or a coherently rewritten prefix. Those need the existing ledger verification and an independently retained checkpoint. The Go-generated fixture includes Unicode and is checked by both native and browser implementations.

Per-entry details display target, recorded live-call evidence and input/output SHA-256. Provenance is taken from digest-covered payload bytes when supplied, rather than a separate unbound display context. Explicit boolean live-call evidence is shown as yes/no; the native recorded adapter is known not to invoke a live model. Adapter configuration and hashes alone remain unknown. Invalid or absent hashes are unavailable. No provider call or invocation truth is inferred from an adapter name.

A shared resource-scoped notification component lives in the same Audit view, supporting #373 without a second feed app. The operator chooses a visible audit resource and starts polling, pauses, or manually refreshes. The existing authorized GET returns up to 100 events. The UI accepts only matching resource pages and matching event rows, deduplicates IDs and escapes values. It polls every 10 seconds while active and visible. Selection, identity, access, read failures and detachment invalidate pending responses. Missing reads do not mean no events occurred. This is not a complete authorization history or a durable push stream; that broader delivery work remains in #373/#380.

This native proof projection is registered as `reporting.AuditProjectionProof` and marked `CONDUIT_NATIVE`. It makes no private Apollo transport or checkpoint compatibility claim. The view enhancements are tracked in #557.
